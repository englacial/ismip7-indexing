# Phase C adversarial review (clean-context Opus, 2026-11-01)

Reviewed commit d3ae842 (`ismip7_helper/lambda_handler.py`, `ismip7_helper/fanout.py`, `Dockerfile.lambda`, `docs/lambda.md`, the process-pool path of `virtualize.concat_group`). The reviewer could not build the image (the proxy blocks the public ECR layer CDN), so Dockerfile findings come from reading and wheel tags. "Confirmed" means reproduced; probe scripts are in the session scratchpad (`shm_probe.py`, `pipe_pool.py`, `creds_probe.py`, `exists403.py`, `ctrlc.py`).

## Findings, most severe first

**1. virtualize.py:596-610 with lambda_handler.py:142-154. On Lambda every invocation fails: `ProcessPoolExecutor` needs POSIX semaphores and Lambda has no `/dev/shm`. Confirmed by simulation.**
`workers()` returns 6 at 10 GB so `use_processes=True`. `ProcessPoolExecutor` builds a `multiprocessing.Queue` (BoundedSemaphore + Lock) and a `SimpleQueue` (Lock); each is a `SemLock` calling `sem_open` on `/dev/shm`, under any start method. Making `SemLock` raise ENOSYS gives `OSError: [Errno 38]`; in a mount namespace with read-only `/dev/shm`, `test_run_event_writes_and_verifies` fails with `OSError: [Errno 30] Read-only file system`. Effect: the fan-out gets 1,500 quick "failed" records. AWS's guidance is `Process` + `Pipe`. A thread fallback is not enough: 1,815 × 1.2 s / 2 ≈ 1,090 s exceeds 900 s. Fix: semaphore-free workers (`ctx.Process` per worker with a slice of items and a `ctx.Pipe(duplex=False)`; each sends back pickled `[("ok", OpenedFile) | ("err", exc)]`; parent receives, joins, re-raises the first error); `pipe_pool.py` is a working prototype under forkserver and spawn with read-only `/dev/shm`. Test by monkeypatching `_multiprocessing.SemLock` to raise `OSError(ENOSYS)`. Before deploying, run the image under the Lambda Runtime Interface Emulator as a non-root user with an unwritable `/dev/shm`.

**2. docs/lambda.md:9-18 and lambda_handler.py:128. The largest groups do not fit in 900 s even with working processes, and nothing protects against this.**
The table assumes perfect 6x scaling. With the measured process efficiency (about 3.9x on 6 vCPUs): 3,146 × 1.2 s / 3.9 ≈ 970 s for the 8 km / 4 km ssp groups, 3,146 × 1.5 s / 3.9 ≈ 1,210 s for the 2 km / 1 km ssp groups, before concatenation, commit, verification and cold start. Every ssp SMB group would burn 900 s × 10 GB and return `Sandbox.Timedout`. The docs mention a non-existent `--max-files`. The handler ignores `context` (no deadline, no partial progress). Fix: (a) measure seconds per file on Lambda first; (b) have the fan-out route groups whose estimate exceeds ~700 s to a big EC2 box running `ismip7-virtualize` (which needs a `--workers` option); or (c) split groups into map invocations writing pickled `OpenedFile`s to S3 scratch plus one reduce step; (d) check `context.get_remaining_time_in_millis()` after opening and return `status: failed, error: "deadline"` rather than being killed. Fix the docs table.

**3. fanout.py:125-141. Ctrl-C does not stop the fan-out; every queued group is still invoked and its result thrown away. Confirmed.**
`as_completed` raises, then `ThreadPoolExecutor.__exit__` calls `shutdown(wait=True)` without `cancel_futures`. After Ctrl-C the laptop keeps invoking all remaining groups for hours, nothing is recorded, the report is never written, and a "resume" re-run collides with the orphaned writes (same-group conflicts; with overwrite, mutual deletes). Fix: `try/except KeyboardInterrupt`, `pool.shutdown(wait=False, cancel_futures=True)`, write in-flight group paths to the report as `status: "in-flight"`, print that they may run for up to 15 minutes. Test with a fake invoke and `_thread.interrupt_main`.

**4. fanout.py:82. The synchronous-invoke transport loses results that succeeded.**
`read_timeout=900` equals the function timeout, so a group finishing near 890 s plus init raises `ReadTimeoutError` and is reported failed though committed. No TCP keepalive: NATs drop 15-minute idle connections (AWS NAT Gateway at 350 s). `max_pool_connections` defaults to 10 against 40 threads. Fix: `Config(read_timeout=960, tcp_keepalive=True, max_pool_connections=concurrency)`; consider async invokes with the handler writing its `GroupRun` to S3, or run the fan-out from EC2/CloudShell in us-west-2. `retries={"max_attempts": 0}` is correct and must stay (default retries would start a second concurrent invocation of the same group).

**5. lambda_handler.py:50. Every INFO line is dropped on Lambda. Confirmed.**
The Lambda runtime installs a root handler before import, so `logging.basicConfig` is a no-op and the root stays at WARNING; notes for a 3,000-file group exist nowhere. The import-time `basicConfig` also changes logging for importers. Fix: set the root level in `handler()` (or `basicConfig(force=True)`), drop the import-time call, add `n_notes` and the first notes to `GroupRun`.

**6. lambda_handler.py:53-88, 141. Write credentials that expire mid-run fail at commit, after all the work; a stale secret is re-read on every S3 request. Confirmed.**
With `expires_after` in the past the callback runs per HTTP request. Expired at start fails fast (`ExpiredToken`), but credentials valid at start and expiring mid-run fail at `session.commit`. The callback is picklable (`SecretCredentials`), a secret without `Expiration` is never refreshed, and `ISMIP7_WRITE_CREDS_JSON` silently wins over the secret. Fix: fetch once in `target_from_event` and refuse when `expires_after < now + remaining time + margin`, naming the expiry; same check in the fan-out before invoking; document the `Expiration` requirement.

**7. docs/lambda.md:25 and Dockerfile.lambda. The documented build is likely to produce an image Lambda rejects.**
`docker build` on Apple silicon yields arm64 while `create-function` defaults to x86_64; Docker Desktop/buildx add provenance attestations (OCI index) that Lambda rejects. Use `docker buildx build --platform linux/amd64 --provenance=false` (or `--architectures arm64`). Smaller: `[index]` pulls pyarrow (167 MB) and boto3 (already in the base); netCDF4 unused at runtime; `UV_CACHE_DIR` is dead; a missing `--build-arg GIT_SHA` silently records ""; no `.dockerignore`. glibc is fine (manylinux_2_28 wheels on AL2023).

**8. lambda_handler.py:135. `run_event` can raise despite its contract. Confirmed.** `event["group_path"]` is outside the `try`; an empty `keys` list gives a misleading message. Fix: move inside, `event.get("group_path", "?")` in the fallback, explicit "no keys" error.

**9. virtualize.py:689-693, 604. Worker overhead on every file and invocation.** `_open_in_process` builds a new obstore S3 client per file (~3,100 TLS setups per group): cache the registry per process. Every forkserver child re-imports xarray/virtualizarr/h5py: use `ctx.set_forkserver_preload(["ismip7_helper.virtualize"])`. An injected `registry=` is silently ignored in process mode.

**10. fanout.py:184-190, 211, 179. Smaller issues.** No fail-fast for an S3 target without `--write-creds` (falls back to the laptop's AWS credentials); `--aws-region` is conflated with the target bucket's region; a `local:` target with `--function` creates the repo on the laptop so every Lambda fails; `--max-groups` differs between `--dry-run` and real runs; reports are overwritten on re-run (suggest a timestamped default).

## Probe results
`/dev/shm` and the executor: confirmed; plain `ctx.Process` + `Pipe` works under forkserver and spawn without a writable `/dev/shm`. Opening the repository before the pool with forkserver: sound (fork+exec, not a bare fork of the threaded parent). `_open_in_process` in a fresh worker: pickled by reference, `/var/task` resolves. `os.cpu_count()` on Lambda: refuted as a concern (Firecracker guest sees only its vCPUs; 10,240 MB reports 6); record it in `GroupRun` on the first run. Read-only filesystem: no writes outside `/tmp`. Memory: fine (~300 MB of coords for 3,100 files plus ~6 × 200 MB interpreters). Event size: 0.42 MB for 3,146 files against the 6 MB limit; `GroupRun` serialises. Cold start: ~1 GB image, 40–50 cold starts per run, negligible. boto3 retries: `max_attempts: 0` correct.

## Checked and found sound
`make_event` sorts keys and carries sizes so a retry yields the same digest; `plan_groups` skip logic agrees with `--overwrite`/`--verify`; `ensure_hierarchy` runs before any invoke; `on_result` runs on the main thread; the final report is sorted; transport and `FunctionError` failures become records; `Executor.map` cancels pending opens on a failure; `VirtualizeError` and `OpenedFile` pickle; repository-not-found, missing credentials, unparseable keys and wrong group are reported not raised; `handler()` accepts a string event; a timeout leaves the store consistent.

- **1 accepted.** `concat_group(use_processes=True)` no longer uses `ProcessPoolExecutor`. `virtualize._open_with_processes` starts `n` forkserver `Process` workers (`set_forkserver_preload(["ismip7_helper.virtualize"])`). Each worker gets a slice of `(key, size, url)` items and a `Pipe(duplex=False)`, and sends one pickled `("ok", OpenedFile)` or `("err", exc)` per file. The parent reads with `connection.wait`, stops the other workers on the first error and raises it as `VirtualizeError`. A worker that dies without sending all its results is an error too. Results come back in input order. Threads are used only when the processes cannot start (`OSError` at start, logged at WARNING). Tested: the `_multiprocessing.SemLock` ENOSYS mock, processes equal threads, error propagation, the start-failure fallback. Also checked by hand with a read-only tmpfs on `/dev/shm`.
- **2 accepted, options (b) and (d).** `ismip7-virtualize --workers N` opens files in N processes. The fan-out estimates `n_files × --seconds-per-file (1.3) / --speedup (3.9)`. There is no deferral with `--local`. Given a Lambda context, the handler returns `failed`/`"deadline"` with its timings when less than 90 s remain after opening. `GroupRun` gains `cpu_count`, `n_workers` and `timings` (`open`, `commit`, `remaining_after_open`). docs/lambda.md has the 3.9x table and the deferral, and says the per-file seconds must be measured on Lambda in the first run.
